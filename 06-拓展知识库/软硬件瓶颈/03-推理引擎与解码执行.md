# 推理引擎与解码执行

> **学习导航**：承接生成机制和性能瓶颈；本课划分模型、解码策略与推理引擎责任；完成后应能解释 vLLM 等平台为什么影响执行与性能，却不决定模型知识质量。

## 本课目标

画出 `请求 -> tokenizer -> 模型前向 -> logits -> 解码策略 -> token -> 调度与缓存 -> 输出`，并标记每步由谁实现。

## 为什么要学这一课

初学者容易把“采样代码运行在 vLLM 中”理解成“回答质量由 vLLM 创造”。实际质量来自权重、上下文、模板与解码共同作用；引擎负责正确高效地执行、调度和管理内存。分清责任才能正确比较模型与平台。

## 四个不同对象

| 对象 | 主要职责 |
|---|---|
| 模型权重 | 根据输入计算 logits |
| 解码策略 | 按 greedy、temperature、top-k、top-p 等选择 token |
| 推理引擎 | 执行前向、缓存、batch、调度、并行和服务接口 |
| 应用工作流 | 组织提示、检索、工具、权限和最终结果 |

同一模型在不同引擎上应该保持可解释的数值与输出关系，但精度、随机数实现、模板、默认参数或 bug 可能造成差异，因此需要固定配置做回归。

## 五个引擎机制

- **连续批处理**：请求到达和结束时动态加入或退出 batch，提高设备利用。
- **分页 KV Cache**：以块管理缓存，降低碎片并支持更多并发。
- **前缀缓存**：复用完全相同且权限允许的前缀计算。
- **分块预填充**：把超长 prefill 拆到多个调度步，减少它对正在 decode 请求的 TPOT 干扰。
- **Attention 后端与图执行**：选择适合形状和硬件的 kernel，并用图捕获或编译降低重复启动开销。

这些机制主要改变吞吐、延迟和容量，不会把外部新事实写进模型参数。

## 三个请求看懂动态调度

假设每个调度步最多处理 6 个 token 单位，A、B 正在 decode，C 是 10-token 新 prompt：

| 调度步 | A | B | C | 说明 |
|---|---:|---:|---:|---|
| 1 | 1 | 1 | 4 | 先推进两个在途请求，剩余预算处理 C 的首个 prefill 块 |
| 2 | 1 | 完成退出 | 5 | B 释放请求槽和 KV 块，C 继续 prefill |
| 3 | 1 | - | 1 | C 完成 prefill，之后才能进入逐 token decode |

这张表不是某个引擎版本的逐行实现，而是统一 token 预算的教学模型。分块让 A 的每步等待更稳定，却可能让 C 的 TTFT 比一次性完成 prefill 更长。

## 缓存命中也有语义条件

前缀缓存只在 token 序列完全一致、模型与适配器一致、缓存仍有效且权限允许时复用。两个用户的文档“看起来相似”不等于 KV 可以共享；权限域不同的私有前缀也不能为了性能跨租户复用。

分页管理解决的是 KV 块分配、回收和共享，不会减少模型每个 token 理论上需要保存的 K/V 内容。真正降低每 token KV 大小通常来自 GQA/MQA、低精度缓存、结构变化或更激进的状态压缩。

## 预设案例观察

课程提供两个推理引擎在相同模型、tokenizer、模板、提示、seed 和解码参数下的冻结记录，并附连续批处理、分页 KV、分块 prefill 和图执行的开关对照。比较输出一致性、TTFT、TPOT、P99、有效吞吐和显存；先审查 greedy 数值回归，再解释采样分布差异和调度收益。

## 本课验收

1. 采样发生在引擎中，为什么知识仍主要来自模型权重和上下文？
2. 连续批处理主要改善什么，又可能伤害什么？
3. 前缀缓存为什么必须考虑权限和完全一致性？
4. 两个引擎输出不同，应先固定哪些变量？
5. 分块 prefill 用什么代价换取什么稳定性？
6. 分页 KV 为什么不等于每个 token 的 KV 内容变少？

## 方法边界

不同引擎支持的模型、精度和 kernel 不同，不能假设配置名称完全等价。性能结论必须带软件版本和硬件环境。
