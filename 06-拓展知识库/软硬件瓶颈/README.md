# 软硬件瓶颈

学习导航：承接 Transformer 计算、训练规模化和推理部署；本路线先建立 AI Infra 全栈责任地图，再通过冻结性能记录，把“模型太慢、太贵、放不下”定位到算法、运行时、内核、集群或硬件层。

## 先分清六层责任

| 层 | 典型对象 | 常见瓶颈 | 不能单独解释什么 |
|---|---|---|---|
| 模型算法 | 注意力、MLP、MoE、量化、推测解码 | FLOPs、KV Cache、激活、精度损失 | 实际硬件利用率和服务排队 |
| 框架与算子 | PyTorch、矩阵库、attention kernel | kernel 启动、融合、数值格式、算子缺失 | 请求调度和产品端等待 |
| 编译与运行时 | 图编译、内存规划、通信库 | graph break、数据搬运、同步 | 模型语义能力和数据质量 |
| 推理服务 | vLLM 等引擎、batch、缓存、调度 | 首 token 延迟、吞吐、碎片、尾延迟 | 模型原本学到的知识是否正确 |
| 集群系统 | GPU 间通信、网络、存储、容错 | 带宽、负载不均、检查点、故障恢复 | 单卡 kernel 的全部效率 |
| 硬件 | GPU/加速器、HBM、互联、CPU | 算力、显存容量、显存带宽、能耗 | 软件是否选择了合适算法和布局 |

## 为什么“随机采样”不是 vLLM 决定模型质量

模型前向给出 logits，解码策略定义怎样从 logits 选 token，推理引擎负责高效执行这些步骤。不同引擎可能在精度、随机数、批处理顺序和算子实现上出现可测差异，也可能存在 bug；但它们不会凭空赋予静态权重新知识。部署平台主要决定执行正确性、速度、显存利用和可扩展性，模型权重、上下文与后训练主要决定能力和行为分布。

## 从现象倒推瓶颈

| 现象 | 优先测量 | 常见原因 |
|---|---|---|
| 首个 token 很慢 | TTFT、输入长度、队列时间 | prefill 计算、排队、冷启动、检索链 |
| 生成每个 token 很慢 | TPOT、显存带宽、batch | decode 带宽受限、KV Cache 读取、低并发 |
| 并发增加后尾延迟暴涨 | P50/P95/P99、队列、batch | 调度拥塞、内存不足、长短请求互相阻塞 |
| 模型装不下 | 权重、KV Cache、激活、碎片 | 精度过高、上下文过长、并发过大 |
| 多卡反而更慢 | 通信占比、负载、拓扑 | 张量/专家通信、同步、跨节点网络 |
| 标称算力很高却利用率低 | kernel 时间、算术强度、数据搬运 | 小算子、未融合、带宽瓶颈、CPU 喂数不足 |

## 预设案例：同一模型的服务对照

课程提供同一模型、硬件和请求集合下的两组冻结服务记录，例如单请求与连续批处理、不同 KV Cache 配置、原精度与量化；材料注明 warm-up、软件版本和采样参数。

学习者检查记录是否同时包含 TTFT、TPOT、端到端 P50/P95、tokens/s、峰值显存、错误率和输出质量回归。只报告“每秒多少 token”无法说明单用户体验，也无法说明高并发稳定性。

## 方法边界

- 理论 FLOPs 降低不等于真实延迟按同比例降低，算子和硬件必须支持。
- 量化可能降低容量和带宽，也可能因反量化或缺少 kernel 无法获得预期加速。
- 吞吐提高常以排队和单请求延迟为代价，必须在目标并发下比较。
- 不同 GPU、驱动、框架、引擎和请求分布的结果不能直接横向复制。
- 硬件瓶颈不是纯硬件问题；数据布局、模型结构、调度和编译共同决定最终利用率。
