# 问题合同与两套评测集

> **学习导航**：承接能力路线中的方法选择；本课先定义用户问题和失败代价，再讨论模型；完成后应能写出一份不依赖“使用某模型”措辞的项目合同。

## 本课目标

明确用户、场景、输入、输出、失败代价、数据权限和资源上限，并分清开发评测集与冻结测试集。

## 为什么要学这一课

很多项目从“我要微调一个模型”开始，最后才发现普通规则、检索或现成 API 已能解决，或者根本没有可检查的成功标准。问题合同把技术选择推迟到需求和证据之后，避免为了训练而训练。

## 七个必须回答的问题

1. 谁在什么场景使用结果？
2. 输入来自哪里，可能缺什么或错什么？
3. 输出会影响什么决定？
4. 错答、漏答、延迟和越权分别有什么代价？
5. 哪些资料允许进入训练、上下文或日志？
6. 目标硬件、预算和响应时间是多少？
7. 什么样的测试结果才允许进入下一阶段？

## 示例：工单路由

不要写“训练一个客服大模型”。更可检查的合同是：输入一条脱敏工单，输出 8 个固定类别之一或“信息不足”；高代价类别召回率不得低于 95%，P95 延迟低于 200 ms，模型不能生成面向客户的自由文本。

这份合同已经暗示：分类器或规则可能比生成模型更合适。

## 两套评测集不能混用

在调提示或训练前，先按时间、用户或文档分组切分样本，避免相邻样本泄漏。两套材料都应覆盖正常、长尾、信息不足、冲突、对抗和权限边界，但职责不同：

| 材料 | 什么时候查看 | 负责什么 |
|---|---|---|
| 开发评测集 | 方案开发期间可反复查看 | 比较规则、Prompt、RAG、微调、阈值和候选检查点；失败可进入下一版开发集 |
| 冻结测试集 | 方案、阈值和选择规则冻结后才查看 | 最终估计质量、成本与安全边界；若据此改方案，这批数据便不再是未见测试证据 |

“冻结”不是永远不更新，而是本轮最终评估期间不参与选择。新增线上失败先进入回归候选池；经过裁决、去重和重新切分后，才能进入下一版数据集。

## 预设案例观察

课程提供一页问题合同、开发评测记录和冻结测试快照。检查每条是否标明输入来源、期望输出、失败代价、所属分桶和数据角色，并找出会导致评估失真的缺项。

## 本课验收

1. 为什么“准确率高”不足以定义工单项目成功？
2. 开发评测集和冻结测试集分别允许参与哪些决策？
3. 项目目标为什么不能写成“使用 LoRA 提升效果”？
4. 什么时候普通代码应成为首选方案？

## 方法边界

问题合同不能消除需求变化，但能让变化被记录。业务方、数据负责人和技术负责人应共同确认边界，不能由模型指标单方面替代。
