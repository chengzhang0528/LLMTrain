# 基础设施与评测

## 学习目标

把“模型能运行”和“比较结果可信”连接起来。大模型系统里，公式、内核、通信、缓存和评测外壳会共同决定最终数字。

## 固定状态如何兑换成系统收益

软最大注意力做上下文并行时，设备间常要交换随序列增长的 K/V 块。KDA 的历史被压进固定形状状态，给跨设备通信提供了不随 token 数增长的目标。

困难在于 delta 更新不满足“各设备从零计算，最后简单求和”。KDA Context Parallelism 将一段序列的作用拆成对传入状态的转移和从零产生的新状态，再交换固定大小摘要并做前缀组合。这里最重要的不是记住 KCP，而是看到：算法的代数性质决定了能否并行。

## MoE 与内存调度

专家并行要求把 token 发往拥有目标专家的设备。负载不均会让部分设备等待或缓冲区按最坏情况预留。MoonEP 试图在保持专家选择的同时重新安排计算位置，使各 rank 获得相同数量的 token–expert 对；相关上界让缓冲区可以按证明而不是经验猜测设置。

其他基础设施技术可归纳为三类交换：

| 紧张资源 | 常见交换 | 需要检查 |
|---|---|---|
| 显存 | 重算、量化、卸载、复用生命周期不重叠的缓冲区 | 多花多少计算、带宽或精度 |
| 带宽 | 缓存状态、存重放原料而非结果 | 重放算力和一致性成本 |
| 利用率 | 流水线、动态限流、填充空泡 | 长尾、调度和故障恢复 |

## 评测九问

看到分数先记录条件，再比较数值：

1. 谁运行、谁判分？
2. 使用哪个模型版本和日期？
3. agent harness 与系统提示是什么？
4. 有哪些工具、外部搜索或 Python？
5. 推理努力、温度、top-p 和总预算是什么？
6. 上下文窗口如何管理、压缩或截断？
7. 是否存在拒答、回退或失败重试？
8. 使用哪个任务子集、硬件、重复次数和汇总方式？
9. 每任务成本、延迟和成功率是否同时报告？

例如同一 K3 在 BrowseComp 上使用 300K token 触发的上下文压缩时报告 91.2；使用完整 1M 上下文但不做上下文管理时报告 90.4。差异提醒我们，排行榜条目是“模型 + 外壳 + 配置”的结果。

## 四级练习

**L1 · 直接应用**：为什么 KDA 固定状态的通信量不随序列长度增长，不能推出端到端延迟也不增长？

<details><summary>参考答案</summary>

本地 token 计算、块内矩阵运算、前缀组合、其他 MLA 层和生成长度仍会增长。固定的是某一类跨设备状态通信。

</details>

**L2 · 变形迁移**：某评测只报告平均成本，为什么还应看分布？

<details><summary>参考答案</summary>

长时程任务常有重尾，少数极长请求可能决定容量、超时和高分位延迟；平均值会掩盖这些生产风险。

</details>

**L3 · 构造反例**：构造一个缓存命中率很高但总体收益很小的工作负载。

<details><summary>一种构造</summary>

大量请求命中很短前缀，真正昂贵的长请求几乎都不命中。按请求计命中率很高，按节省 token 或时间计收益很小。

</details>

**L4 · 多概念综合**：为什么“同一 benchmark”仍可能不是公平比较？

<details><summary>参考答案</summary>

模型版本、harness、工具、推理预算、上下文策略、回退、硬件、任务子集和判分器都可能不同。benchmark 名称只标识题库，不自动统一整个实验。

</details>
