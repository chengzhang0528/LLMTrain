# GLM-130B：开放规模化训练

> 学习导航：这篇报告把“参数变大”还原成一套工程账本：数据、并行、稳定性、评测和开放权重必须同时成立。

## 论文回答什么

130B 不是一个神奇的数字。报告要解决的是：在双语数据和有限硬件下，如何训练一个足够大的开放基座，并让读者知道它用了什么数据、并行策略和评测条件。对初学者来说，重点不是记住参数量，而是学会把规模、训练计算和能力分开。

## 真实场景与信息流

预训练样本先经过清洗、去重和 tokenizer，分成中文、英文和代码等来源；数据批次进入张量并行、流水线并行和数据并行的集群，最后更新同一份权重。任何一个环节改变，结果就不再是“只扩大参数”的对照。

```mermaid
flowchart LR
  A[多语言原始语料] --> B[清洗/去重/词元化]
  B --> C[数据并行：不同批次]
  C --> D[张量/流水线并行：切分计算]
  D --> E[梯度同步与优化器]
  E --> F[130B 权重检查点]
  F --> G[统一评测与模型卡]
```

## 核心机制：规模化的四本账

1. **容量账**：总参数、层数、宽度和词表大小决定可表示的函数空间。
2. **计算账**：训练 token 数与每 token FLOPs 决定花了多少计算，不等于参数量。
3. **通信账**：切分矩阵和流水线会产生 all-reduce、发送激活和等待气泡。
4. **证据账**：分数必须绑定数据集版本、提示模板、是否 few-shot 和评测脚本。

总参数 130B 只能回答“模型容量大约多大”；不能推出显存一定需要 130B × 4 bytes，也不能推出某个下游分数按比例增长。精度、分片、激活检查点和优化器状态都会改变真实占用。

## 训练与推理分开

训练阶段最怕吞吐下降和数值不稳定：大 batch、学习率、梯度裁剪、混合精度和检查点恢复共同决定是否跑完。推理阶段更关心权重显存、KV Cache、并发和首 token 延迟；训练并行方案不能直接当成服务方案。

## 数字证据账本

| 读到的数字 | 口径 | 不能直接推出 |
|---|---|---|
| 130B 参数 | 总参数规模 | 每 token 激活量或服务成本 |
| 训练 token/数据配比 | 报告中的训练计划 | 数据质量和去重效果已被单独证明 |
| 下游基准分数 | 作者评测 | 所有中文用户任务都同幅度提升 |
| 并行规模与训练时长 | 集群配置 | 另一种 GPU、网络或 batch 仍能复现 |

教学复核：若每张卡只保存总权重的 1/8，权重分片约为 $130\text{B}/8=16.25\text{B}$ 个参数；这还没有算梯度、优化器、激活和通信缓冲区。因此“分片后就能在一张卡上运行”是错误结论。

## 代价与边界

- 双语或多语数据比例会改变各语言的 token 效率和能力，不存在脱离数据配比的“通用规模规律”。
- 开放报告提供的配置未必包含全部清洗规则、故障重试和硬件细节，复现要标记待核查。
- 大模型可以更好地拟合模式，但数据污染、评测过拟合和事实陈旧仍然存在。

## 本课验收

**L1 · 直接应用**：130B 表示哪一本账？

<details><summary>参考答案</summary>

它首先表示总参数容量；还要查精度、分片、激活参数和优化器状态，才能估计训练或推理资源。

</details>

**L2 · 变形迁移**：为什么训练吞吐高不等于用户首 token 延迟低？

<details><summary>参考答案</summary>

训练吞吐按批量处理许多 token；首 token 延迟还受权重加载、prefill、网络、调度和服务批处理影响。

</details>

**L3 · 构造反例**：同样 130B 参数，怎样出现明显不同的中文能力？

<details><summary>参考答案</summary>

中文数据比例、质量、去重、训练 token 数、tokenizer 和后训练提示模板不同，都可能造成差异。

</details>

**L4 · 多概念综合**：评估开放模型时，为什么要同时记录模型卡、评测脚本和硬件？

<details><summary>参考答案</summary>

模型卡给版本和配置，脚本给指标口径，硬件和推理预算决定速度与可复现条件；缺一项就容易把系统差异误当模型能力。

</details>

## 方法边界

本页不声称 GLM-130B 的每个工程细节都已独立复现；所有数字都应回到报告版本和模型卡。规模化经验可以迁移为“记账方法”，不能直接迁移成另一家模型的最优并行配置。
