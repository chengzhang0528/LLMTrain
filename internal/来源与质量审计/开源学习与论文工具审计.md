# 开源学习与论文工具审计

核查日期：2026-08-09。来源材料列出 20 个高关注开源项目，本页逐项核对官方仓库、README、许可证和维护状态，并记录本站采用决定。Star 只表示关注度快照，不参与课程主线排序。

## 总结结论

值得吸收的是教学结构和证据流程：从第一性原理逐层构建、让公式与代码同屏对应、把参考实现与优化实现分开、按研究问题选择论文，以及让 AI 问答先检索证据再生成答案。

不应吸收的是：把高 Star 当质量排名、把能启动当作复现、把资源目录当成课程、要求初学者跟随快速老化的 Notebook、把 AI 摘要当精读完成，以及忽略代码、书籍图片、模型权重和数据各自的许可证。

## 大模型学习项目

### Microsoft Generative AI for Beginners

[官方仓库](https://github.com/microsoft/generative-ai-for-beginners)，MIT。优点是每课包含概念、示例、挑战和延伸阅读，适合吸收“一个单元形成闭环”的组织方式。局限是大量示例依赖 OpenAI、Azure 或 Microsoft Foundry；README 已提示 GitHub Models 于 2026 年 7 月结束，说明服务绑定内容会快速老化。本站不采用其云端实操路线。

### LLMs from Scratch

[官方仓库](https://github.com/rasbt/LLMs-from-scratch)，`LICENSE.txt` 为 Apache-2.0，但明确排除与书籍相关的特定内容和图片。它从文本数据、注意力、GPT、预训练推进到分类与指令微调，最值得吸收的是“同一个模型逐章长大”和章节、练习、代码互相对应。本站不复制书中图片，也不把 Python 前置和实际训练设为学习门槛。

### LLM Course

[官方仓库](https://github.com/mlabonne/llm-course)，Apache-2.0。它用 LLM Fundamentals、LLM Scientist 和 LLM Engineer 区分角色路线，适合吸收“按目标角色分流”。但仓库主体包含大量外部文章、Colab 和一键工具，不是单一实现逐层长成的课程；本站只借鉴路线分层，不采用工具清单式教学。

### nanoGPT

[官方仓库](https://github.com/karpathy/nanoGPT)，MIT。`model.py` 与 `train.py` 的最小边界仍适合阅读模型定义和训练循环，但作者已在 README 明确标记项目很旧且已弃用，并推荐新的 [nanochat](https://github.com/karpathy/nanochat)。本站把 nanoGPT 降为历史源码样本，不再称为当前首选训练系统。

### self-llm

[官方仓库](https://github.com/datawhalechina/self-llm)，Apache-2.0。它对中文模型家族、Linux、不同 GPU/NPU 平台、部署与 LoRA 路线覆盖较广，适合核对“同一方法在不同模型和硬件上的环境差异”。局限是教程数量多、依赖组合复杂且版本漂移快；本站只吸收模型/硬件责任矩阵，不要求学习者安装或运行。

### llm.c

[官方仓库](https://github.com/karpathy/llm.c)，MIT。项目把 PyTorch 参考实现、CPU 单文件实现、CUDA 优化实现、数值对照测试和多 GPU 路线分开，最值得吸收的是“先有可读参考，再做性能优化，并用测试证明两者一致”。它需要 C/CUDA、cuDNN 和具体硬件知识，不是初学者主线。

### Hands-On Large Language Models

[官方仓库](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models)，Apache-2.0，是配套书籍代码仓库。它重视直觉图、章节 Notebook 和从表示到应用的桥接，适合吸收视觉解释与章节产物设计。仓库建议使用 Colab/T4，且近 300 张定制图属于配套书的重要内容；本站不复制这些图，也不把 Colab 作为课程运行依赖。

### llm-action

[官方仓库](https://github.com/liguodongiot/llm-action)，Apache-2.0。训练、并行、通信、推理、压缩、RAG 与硬件目录覆盖很广，适合作为工程术语和责任层的查漏来源。不同目录的原创性、深度、技术栈和验证方式并不统一，不能直接充当一条无重复的学习主线。

### nn-zero-to-hero

[官方仓库](https://github.com/karpathy/nn-zero-to-hero)，MIT。它从 Micrograd、字符模型和手写反向传播逐步走向 GPT，视频、Notebook 和练习紧密对应。真正有价值的是“先亲手预测和推导，再揭示答案”的主动学习节奏；它本身明确不适合只被动观看。本站吸收预测、分步揭示和闭卷重建，不要求运行 Notebook。

### llm-universe

[官方仓库](https://github.com/datawhalechina/llm-universe)。它以中文小白为目标，把 Prompt、文档处理、RAG、框架和评估接成应用路线，适合补充“一个问题怎样进入完整应用链”。GitHub API 与仓库根目录未识别到许可证，且框架/API 依赖会快速变化；本站只链接和独立分析，不复制内容或实现。

### nanochat：指南遗漏的当前继任者

[官方仓库](https://github.com/karpathy/nanochat)，MIT。它覆盖 tokenizer、预训练、微调、评测和推理的完整模型生命周期，是 nanoGPT 更合适的当前对照。其参考速度路线面向 8×H100 等高成本环境，本站只吸收“单一 harness 串起全生命周期、明确成本口径和失败样例”，不把实际训练设为课程任务。

## 论文选择与人工精读项目

### Papers We Love

[官方仓库](https://github.com/papers-we-love/papers-we-love)。它擅长社区策展和按计算机领域发现经典论文，不提供稳定的知识依赖图，也不是精读或复现课程。仓库未检测到许可证；本站只把它当论文发现入口，不复制目录内容。

### Deep Learning Papers Reading Roadmap

[官方仓库](https://github.com/floodsung/Deep-Learning-Papers-Reading-Roadmap)。它体现了按历史里程碑与主题安排论文的早期方法，但最近代码推送停留在 2022 年，主结构形成于现代 Transformer/LLM 浪潮之前，仓库也未检测到许可证。本站只保留“先建立历史依赖”的思想，不采用其现成顺序。

### mli/paper-reading

[官方仓库](https://github.com/mli/paper-reading)，Apache-2.0。它通过逐段视频精读，把研究问题、论点、公式、实验和论文表达放在一起，尤其值得吸收“理由、论据、担保”和“作者讲了什么故事、证据是否撑得住”的质疑方式。仓库本身主要是论文与视频目录，不是代码复现系统。

### ML Papers Explained

[官方仓库](https://github.com/dair-ai/ML-Papers-Explained)。它覆盖大量论文和主题，适合发现关键词与快速获得二手直觉；条目深度和证据完整度不统一，且仓库未检测到许可证。本站不把二手摘要当论文证据，也不复制其解释文字。

### Annotated Transformer

[官方仓库](https://github.com/harvardnlp/annotated-transformer)，MIT。它把论文文字、公式和实现组织在同一份可生成 Notebook 的源文件里，是“公式对象映射到代码”的经典范例。实现对应原始 Encoder-Decoder Transformer，并不代表现代 Decoder-only、RoPE、FlashAttention 或 MoE；本站吸收注释结构，不复制为现代模型施工图。

### labml annotated implementations

[官方仓库](https://github.com/labmlai/annotated_deep_learning_paper_implementations)，MIT。它用文档站把解释和简单 PyTorch 实现并排呈现，并覆盖 Transformer、LoRA、扩散、GAN 和优化器等多个方向。适合作为“一个公式紧跟一段可读实现”的方法样本；教学实现仍可能省略生产优化、完整复现和版本兼容，不应因有代码就宣称复现论文指标。

## AI 辅助论文工具

### gpt_academic

[官方仓库](https://github.com/binary-husky/gpt_academic)，GPL-3.0。它的函数插件、模型接口、前端和论文/代码解析分层值得研究，覆盖总结、翻译、润色和多模型调用。系统依赖大量模型接口和配置，README 中“本地项目所以 key 很安全”之类表述不能替代威胁建模；API 提供方、日志、代理、插件和上传内容仍需单独审查。

### ChatPaper

[官方仓库](https://github.com/kaixindelele/ChatPaper)，许可证为 CC BY-NC-ND 4.0，包含“禁止演绎”限制。它展示 arXiv/PDF 获取、章节处理、总结、翻译和审稿的流水线，但 README 中部分 API 获取建议和安全表述已经不适合作为当前安全指南。本站只做独立分析和链接，不改编其内容或代码，不让学习者上传未发表材料。

### PaperQA2

[官方仓库](https://github.com/Future-House/paper-qa)，Apache-2.0。默认算法明确拆为候选论文搜索、文档切分与嵌入、证据汇总和重排、基于证据生成回答；仓库还包含源码、测试与文档，是 AI 论文问答中最值得吸收的责任分层。它默认仍依赖模型和嵌入服务，引用存在不支持主张、漏检反例和版本冲突的风险。

### arxiv-sanity-preserver

[官方仓库](https://github.com/karpathy/arxiv-sanity-preserver)，MIT。它展示不依赖生成式模型的论文抓取、文本特征、相似度、个性化排序和网页浏览流程，方法史价值很高。但最近代码推送停留在 2021 年，依赖旧式 MongoDB、ImageMagick 和处理脚本，不适合作为当前系统实现基线。较新的 `arxiv-sanity-lite` 也主要用于理解传统检索推荐，而非现代论文证据问答。

## 本站统一采用原则

1. 按学习问题选项目，不按 Star 排名选项目。
2. 课程吸收方法结构，正文、例子、图和交互必须独立撰写。
3. 代码许可证、书籍图片、论文内容、模型权重和数据许可证分别核对。
4. 已弃用或长期不维护的项目只作历史样本，不作为当前推荐环境。
5. 教学代码用于理解责任边界；没有测试、版本和结果对照时，不称为论文复现。
6. AI 论文工具只能辅助发现、定位和组织证据；结论必须回到原文，敏感材料默认不上传外部服务。

这些结论已转译到内部的[论文课件生产规范](论文课件生产规范.md)。学习者看到的是按照该规范制作完成的论文知识图谱、系列路线和单篇课件，而不是生产检查清单本身。
