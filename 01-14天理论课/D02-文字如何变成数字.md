# D02：文字如何变成数字

> **学习导航**：承接 D01 的“文本先变成 token 才能进入模型核心”；本课追踪文字到 token、ID、查表向量和上下文化表示；完成后应能看着一个例子指出每次变化后的对象类型。

> **主线位置**：[模型原理总纲](模型原理总纲.md) -> D01 条件预测 -> **D02 输入表示** -> D03 数学 -> D04 学习机制。本课只解释输入怎样成为可计算对象，不提前把这些数字说成已经理解了语义。

## 今日目标

能沿着 `文字 -> token -> ID -> Embedding -> 隐藏状态` 追踪一次表示变化，并区分 token、token ID、词表、Embedding、上下文化隐藏状态和位置信息。

## 为什么要学这一课

聊天 API 可以接收汉字或英文字符串，但 Transformer 模型核心不会直接对字符串做矩阵计算。应用或推理框架先调用 tokenizer 得到整数 ID，模型再通过 Embedding 查表得到向量。这个接口边界不等于模型不能形成语义表示：语义相关的规律会在训练所得参数和后续上下文计算中体现出来。分词方式会改变序列长度、训练成本、多语言表现和生成边界；Embedding 负责把离散 ID 接入连续计算。不理解这条转换链，后面看到张量形状、注意力输入和词表采样时就只能背名词。

> **本课范围**：这里只讲文本输入。图像可能先被切成小块，音频可能先变成帧或声学特征；多模态模型会再把这些输入映射成主干可以处理的向量，但不应把它们都误认为由同一个文本 tokenizer 处理。完整差异见 [D14：多模态、应用全景与总复习](D14-多模态、应用全景与总复习.md)。

## 先用一条句子走完四步

先假设 tokenizer 已经训练和配置完成，词表中有 6 个 token：

| token | ID（程序索引） | 人从第一行开始数 |
|---|---:|---:|
| 我 | 0 | 第 1 行 |
| 爱 | 1 | 第 2 行 |
| 学 | 2 | 第 3 行 |
| 习 | 3 | 第 4 行 |
| 学习 | 4 | 第 5 行 |
| `<eos>` | 5 | 第 6 行 |

这里必须先解决一个常见疑问：**token ID 通常从 0 开始**。因此 ID `4` 是索引 4，也就是人从第一行数起看到的第 5 行。后文说“查某一行”时，实际指的是“按 ID 这个零起点索引取值”。

现在把“我爱学习”送入这个玩具 tokenizer：

1. **字符串**：`我爱学习`。
2. **token 序列**：`我 / 爱 / 学习`。这里共有 3 个位置。
3. **ID 序列**：`[0, 1, 4]`。数字保留 token 的先后，但数字大小不表达语义大小。
4. **查表向量**：分别读取 Embedding 表的索引 0、1、4。

假设每个 token 的 Embedding 只有 3 个数字：

```text
E[0] = [ 0.2, -0.1,  0.7]  # “我”
E[1] = [-0.3,  0.8,  0.1]  # “爱”
E[4] = [ 0.6,  0.4, -0.2]  # “学习”
```

把四个字母和具体数字对应起来：

| 符号 | 表示什么 | 本例数值 |
|---|---|---:|
| `V` | 词表大小 | 6 |
| `B` | 本次同时处理的序列数 | 1 |
| `T` | 每条序列的 token 位置数 | 3 |
| `D` | 每个位置的向量坐标数 | 3 |

所以 ID 张量的形状是 `(B,T) = (1,3)`，里面是整数 `[0,1,4]`；查表后的形状是 `(B,T,D) = (1,3,3)`，共有 3 个位置，每个位置放 3 个浮点数。Embedding 表本身的形状是 `(V,D) = (6,3)`；如果这张表没有被冻结，就有 `6 × 3 = 18` 个可训练数字。

这三个对象的归属也不同：

| 对象 | 在哪里 | 什么时候变化 |
|---|---|---|
| tokenizer 与词表 ID | 模型配套的输入配置 | 通常在训练模型前固定；普通聊天时不会重新学习切分规则 |
| Embedding 表 | 模型参数 | 训练时可被梯度更新；普通推理只读取 |
| 隐藏状态 | 当前请求的中间结果 | 随输入、位置和网络层变化；请求结束后不等于永久写回模型 |

## 训练 tokenizer 与使用 tokenizer 是两件事

真实 tokenizer 可能以字节、字符或子词为基础。一个汉字不保证等于一个 token，一个英文单词也可能被拆成多个 token。上下文窗口按 token 数计算，不按字数计算。

BPE 类方法通常先在一批语料上学习哪些相邻单元值得合并，并把合并规则保存下来。模型训练或聊天时，tokenizer 只是应用这套固定规则，不会因为你刚输入一句新话就临时重训词表。更完整的 tokenizer 训练、语言覆盖与数据关系放在 [D08：训练数据与分词器](D08-训练数据与分词器.md)。

编码和解码通常能在同一 tokenizer 配置下往返，但不要把它理解成“任意切法都能原样恢复排版”。规范化、空格处理、未知字符策略和是否自动加入 `<bos>`、`<eos>` 等特殊 token，都由具体配置决定。

## Embedding 把 ID 变成可计算的向量

ID 只是索引。Embedding 表可以想成一张可训练的二维表，常记为 `E`。读取规则可以压缩成 `E[token ID]`：输入 ID 序列 `[0,1,4]`，就按顺序得到 `[E[0], E[1], E[4]]`。方括号里的 ID 是零起点程序索引，不是数学课里从 1 开始数的自然行号。

开始训练时这些数通常没有我们想要的语义。训练不断调整它们，使模型更善于完成预测目标。相近含义是否靠近，要看训练和度量，不能只凭一张二维投影图断言。

真实模型的 Embedding 往往有数千维。这里的“维”是描述一个表示需要多少个坐标，不代表每一维都对应一个能命名的人类概念。二维、三维小例子只是为了能画图和手算。

## Embedding 只是表示旅程的起点

同一个 token ID 会先查到同一行 token Embedding，但这不是它在所有上下文中的最终表示。加入位置信息并经过 Transformer 层后，每个位置都会结合上下文形成新的隐藏状态：

`token ID` → 初始 Embedding → 第 1 层隐藏状态 → … → 最后一层隐藏状态

例如“苹果很好吃”和“苹果发布新品”可能从相同的“苹果”Embedding 出发，后续隐藏状态却因周围 token 不同而变化。讨论“某个词的向量”时，应继续追问：哪一个模型、哪一层、哪个位置、什么上下文？

ID 到 Embedding 是查表，不是把整数 ID 当作连续数值做“升维”。真正的线性投影发生在线性层中：模型用矩阵把一种表示映射成另一种表示，例如生成 Query、Key、Value，或把隐藏状态映射到词表 logits。

数学补充：[高维表示、投影与降维](../03-数学急救包/08-高维表示、投影与降维.md)。

## 顺序从哪里来

只给注意力 token 表示而不提供任何位置线索，模型不足以区分先后顺序。因此模型需要位置机制。原始 Transformer 在进入网络前加入正弦位置编码；许多现代 Decoder 模型用 RoPE 在注意力层内部处理相对位置，还有架构使用注意力偏置。具体接入点不同，但共同目标都是让模型处理先后和距离。

## 一个重要边界

Tokenizer 决定了交给模型核心的离散单元、ID 对应关系和序列长度成本。换 tokenizer 通常会改变词表大小、切分结果与 token ID；如果不同步适配 Embedding 和相关权重，就不能直接替换进已有模型并假定含义保持不变。

## 站内观察

比较页面预设的两种“机器学习”切分：

- 字符级：`机 / 器 / 学 / 习`
- 子词级：例如 `机器 / 学习`

先预测哪种切分会让序列更短，再对照词表大小、序列长度和遇到生词时的表现。不存在对所有语言和任务都最优的唯一切法，也不需要安装或运行分词器。
