# D07：模型一次运行到底发生什么

> **学习导航**：承接 D02、D05、D06，用一个请求串起应用层、推理引擎、模型前向、KV Cache 和逐 token 输出。学完后，应能说清一次 `prefill` 与多次 `decode`。

> **主线位置**：[模型架构总纲](模型架构总纲.md) -> D05 Attention -> D06 完整模型 -> **D07 一次运行**。完成本课后回到总纲，闭卷区分参数、激活、KV Cache、logits 与解码代码。

## 今日目标

能解释一条请求如何经过模板、分词、Embedding、Transformer、LM Head、解码策略和反分词变成文本；区分模型权重、当前上下文、KV Cache、logits、随机数与推理引擎的责任。

## 为什么要学这一课

“预测下一个 token”没有解释提示怎样进入模型、每层缓存什么、首个 token 为何较慢、后续内容为何逐步流出，也没有说明 vLLM 等引擎的职责。本课把这些概念接成运行链，为幻觉、部署、长上下文、量化和硬件瓶颈定位。

## 先分清三层

| 层 | 本次请求中负责什么 | 不负责什么 |
|---|---|---|
| 应用层 | 组织消息、系统提示、工具结果、权限与展示 | 直接执行 Transformer 矩阵计算 |
| 推理引擎 | 加载权重、组 batch、调度算子、管理显存与 KV Cache、执行解码 | 凭空给模型增加知识 |
| 模型 | 在普通推理中，用已加载且不更新的权重把当前 token 序列变成 logits | 自动核验事实、决定业务权限或永久记住本次对话 |

下面所有编号和形状都是**教学示意**，不对应某个具体模型。不同模型的模板、词表、层数、隐藏宽度、缓存策略和解码实现会变化，但“应用组织请求、模型计算 logits、运行时执行并管理状态、解码策略接受候选”仍是一种有用的基础责任划分。

## 用形状再走一遍

假设预设请求被切成 8 个 token，模型隐藏宽度为 4096，词表大小为 32000：

| 阶段 | 教学示意形状 | 轴的含义 |
|---|---|---|
| `input_ids` | `(1, 8)` | 1 个请求，8 个 token |
| 隐藏状态 | `(1, 8, 4096)` | 每个位置有 4096 个浮点特征 |
| 经过每个 Transformer Block | `(1, 8, 4096)` | 形状可不变，但数值和包含的上下文信息改变 |
| LM Head 输出 | `(1, 8, 32000)` | 每个位置都有一份词表分数 |
| 下一 token 候选 | `(1, 32000)` | 生成时通常读取最后一个位置的 logits |
| 选出的 token | 1 个整数 ID | 追加回序列，开始下一轮 |

这里的“多层”不是把 8 个 token 压成 1 个 token。模型通常保留位置轴，只在最后取适合下一步预测的位置；隐藏宽度与词表大小也不是同一个维度。

## 每轮会变和不会变的东西

| 对象 | 普通生成时是否变化 | 生命周期 |
|---|---|---|
| 模型权重 | 通常不变 | 跨请求复用，只有训练或加载新适配器才改变 |
| 当前 token 序列 | 每轮增加一个或多个系统插入的 token | 当前会话或请求 |
| KV Cache | 随已处理历史增长或被分页管理 | 当前请求，结束后可释放 |
| logits | 每轮重新计算 | 只描述当前下一步候选 |
| 采样随机数状态 | 使用随机采样时会推进 | 由 seed、采样算法和执行实现共同影响 |
| batch 与调度位置 | 可能随其他请求加入或结束而变化 | 推理引擎运行时 |

这张表解释了为什么“模型文件没变”不等于“每次输出必然相同”，也解释了为什么部署引擎会影响数值、随机性、延迟和吞吐，却不是模型知识的主要来源。

## 预设概率样例：怎样选一个 token

候选概率为：

| token | 概率 |
|---|---:|
| 蓝 | 0.50 |
| 晴 | 0.30 |
| 灰 | 0.15 |
| 雨 | 0.05 |

- **Greedy**：选“蓝”。
- **Temperature**：作用在 softmax 前的 logits 上；较低通常让分布更集中，较高通常让分布更平。下表展示的是已经归一化后的示意概率，不能直接把概率乘或除 temperature。
- **Top-k=2**：只保留“蓝、晴”，随后重新归一化。
- **Top-p=0.8**：按概率从高到低累计，保留达到 0.8 所需的最小候选集合（这里是“蓝、晴”），再对保留项重新归一化。

这些策略改变输出分布，不负责核验“蓝”是否符合事实。相同模型、相同上下文和相同解码参数在严格确定性实现中通常可以复现；使用随机采样，或实现存在数值非确定性（例如某些并行归约、精度和调度差异）时，结果可能变化。并发调度不是必然改变答案的原因，必须结合具体实现和日志核对。

## KV Cache 与固定状态不是一回事

标准注意力保存随序列增长的 Key/Value；线性注意力或状态空间模块可把历史压入固定形状的状态，避免单步状态内存线性增长。压缩可能丢失细节，因此固定状态不等于无损记住无限历史。混合架构常让多数层低成本更新，少数标准注意力层补充精确检索。

要比较推理内存，应同时写清层数、状态或缓存形状、数据类型、batch 和上下文长度，不能只比较架构名称。KDA 的状态读写见 [外积与状态矩阵](../03-数学急救包/06-外积与状态矩阵.md)。

## 幻觉放在运行链的哪里看

训练目标与数据塑造参数；上下文提供本次信息；前向计算产生 logits；解码选择 token；应用层负责检索、核验、拒答或工具调用。知识缺口、上下文冲突、推理错误、解码、检索和验证都可能造成幻觉，不能只怪“随机采样”。
