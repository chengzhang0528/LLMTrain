# D07：模型一次运行到底发生什么

> **学习导航**：[模型架构总纲](模型架构总纲.md) -> D06 完整模型 -> **D07 一次运行**；本课用一个请求串起模板、分词、`prefill`、多次 `decode 前向`、KV Cache 与解码。完成后应能按生命周期区分权重、激活、KV Cache、logits、随机数和推理引擎。

## 先记四个运行判断

1. **应用先组装请求，模型只接收模板化后的 token 序列。**
2. **Prefill 处理整段有效提示；decode 通常只处理新位置并读取历史 KV。**
3. **模型前向产生 logits，模型外的解码代码才决定接受哪个 token。**
4. **权重、KV Cache、logits 和随机数状态是四种不同状态，生命周期不能混为一谈。**

## 先分清三层

| 层 | 本次请求中负责什么 | 不负责什么 |
|---|---|---|
| 应用层 | 组织消息、系统提示、工具结果、权限与展示 | 直接执行 Transformer 矩阵计算 |
| 推理引擎 | 加载权重、组 batch、调度算子、管理显存与 KV Cache、执行前向与解码循环 | 凭空给模型增加知识 |
| 模型 | 在普通推理中，用已加载且不更新的权重把当前 token 序列变成 logits | 自动核验事实、决定业务权限或永久记住本次对话 |

下面所有编号和形状都是**教学示意**，不对应某个具体模型。不同模型的模板、词表、层数、隐藏宽度、缓存策略和解码实现会变化，但“应用组织请求、模型计算 logits、运行时执行并管理状态、解码策略接受候选”仍是一种有用的基础责任划分。

|---|---|---|
| `input_ids` | `(1, 8)` | 1 个请求，8 个 token |
| 隐藏状态 | `(1, 8, 4096)` | 每个位置有 4096 个浮点特征 |
| 经过每个 Transformer Block | `(1, 8, 4096)` | 形状可不变，但数值和包含的上下文信息改变 |
| LM Head 输出 | `(1, 8, 32000)` | 每个位置都有一份词表分数 |
| 下一 token 候选 | `(1, 32000)` | 生成时通常读取最后一个位置的 logits |
| 选出的 token | 1 个整数 ID | 追加回序列，开始下一轮 |

这里的“多层”不是把 8 个 token 压成 1 个 token。模型通常保留位置轴，只在最后取适合下一步预测的位置；隐藏宽度与词表大小也不是同一个维度。

## 一个 token 背后是一整栋计算高楼

**关心硬件与性能时再读。**

“预测下一个 token”只概括了**输出接口**，没有描述执行规模。下面固定观察基础 decode 前向的一轮：历史位置的 K/V 已经缓存，本轮主要送入一个新位置；这个位置仍要从底部穿过全部 Transformer Block，楼顶的 LM Head 先产生整个词表的 logits，解码代码最后才接受一个 token。

不要把候选并行误解成“先生成几万条文本再选一条”：

1. **层内并行**：大量矩阵乘加共同合成当前位置的新隐藏表示，不是一个参数对应一个候选。
2. **层间串联**：后一层依赖前一层输出，仍要沿网络深度推进。
3. **词表并行**：LM Head 同时算出所有候选分数；最后舍弃的是未选中的分数，不是已生成的文本分支。

这里的“并行”也不等于“整栋楼所有点在同一个时钟周期一起开工”。Block 之间有依赖，Block 内的 Attention、MLP、归一化和残差操作也有先后关系；大的矩阵运算还会被分块，交给许多计算单元执行。动效把这种**层内的批量并行、层间的顺序依赖**压缩成一片逐层上移的波前，用来建立正确数量感，不用来复刻芯片的逐周期调度。

下面的算法显微镜只展开最后一个 Block 后的教学 RMSNorm，省略了 Block 内归一化的具体计算、多头拆分与合并、注意力输出投影等细节；完整 Block 结构见 [D06：拼出完整 Transformer](D06-拼出完整Transformer.md)。

### 用 7B 教学估算拆开数量级

先只估算密集模型中由参数矩阵主导的部分。设参数量 $P=70$ 亿，并约定一次乘法和一次加法分别计为一次浮点操作，则一轮前向常用近似为：

$$
\text{每 token FLOPs} \approx 2P = 2 \times 70\text{ 亿}=140\text{ 亿 FLOPs}
$$

这个近似没有精确计入随上下文长度变化的 Attention 计算、路由、归一化、通信和算子效率，所以它用于判断数量级，不是速度承诺。若再生成 100 个 token，仅参数主导项就约为 $100\times140$ 亿 $=1.4$ 万亿 FLOPs。

再看权重体积。若每个参数用 FP16 的 2 bytes 保存：

$$
70\text{ 亿参数}\times 2\text{ bytes}=140\text{ 亿 bytes}\approx14\text{ GB}
$$

`14 GB` 是十进制教学估算下的**完整权重体积**，不等于每轮必然精确搬运 14 GB。缓存层级、量化、batch、张量并行、算子融合和硬件利用率会改变实际流量；但在低 batch decode 中，大量权重必须反复可用，因此常常受显存带宽限制。

| 教学规模 | Block 数 | 参数主导近似 | FP16 完整权重体积 | 本轮最终接受 |
|---|---:|---:|---:|---:|
| 7B 密集模型示意 | 32 | 约 140 亿 FLOPs/token | 约 14 GB | 1 token |
| 70B 密集模型示意 | 80 | 约 1400 亿 FLOPs/token | 约 140 GB | 1 token |

表中的 Block 数和词表大小是用于控制变量的教学设定，不对应某个指定模型。真实模型即使参数量同为 7B 或 70B，层数、隐藏宽度、词表、GQA/MQA、权重共享与架构仍可能不同。

### 为什么不是“CPU 就足够了”

CPU 当然可以运行模型，尤其是较小、经过量化且不追求高吞吐的模型。问题在于“能运行”和“能以目标速度服务”不是同一件事。一轮 decode 前向的粗略速度上限同时受两类资源约束：

| 约束 | 粗略判断 | GPU 通常更有优势的原因 |
|---|---|---|
| 计算吞吐 | 设备每秒能完成的有效 FLOPs ÷ 每 token 所需 FLOPs | 大量计算单元可并行执行矩阵乘加 |
| 内存/显存带宽 | 设备每秒能搬运的有效 bytes ÷ 每 token 实际搬运 bytes | 高带宽显存更快把权重与 KV 数据送到计算单元 |

最终速度取两种上限中更低的一项，还会受到 batch、上下文长度、量化精度、内核、通信和调度影响。GPU 不是让模型少算，而是让同一批矩阵运算更并行、让数据更快到位；CPU 也不是“完全不行”，只是模型规模与目标 token/s 会决定它是否够用。

## 每轮会变和不会变的东西

| 对象 | 普通生成时是否变化 | 生命周期 |
|---|---|---|
| 模型权重 | 通常不变 | 跨请求复用，只有训练或加载新适配器才改变 |
| 当前 token 序列 | 每轮追加一个或多个已接受的生成 token；工具结果或应用消息通常在后续调用时另行加入 | 当前会话或请求 |
| KV Cache | 随已处理历史增长或被分页管理 | 当前请求，结束后可释放 |
| logits | 每轮重新计算 | 只描述当前下一步候选 |
| 采样随机数状态 | 使用随机采样时会推进 | 由 seed、采样算法和执行实现共同影响 |
| batch 与调度位置 | 可能随其他请求加入或结束而变化 | 推理引擎运行时 |

这张表解释了为什么“模型文件没变”不等于“每次输出必然相同”，也解释了为什么部署引擎会影响数值、随机性、延迟和吞吐，却不是模型知识的主要来源。

## 预设概率样例：怎样选一个 token

候选概率为：

| token | 概率 |
|---|---:|
| 蓝 | 0.50 |
| 晴 | 0.30 |
| 灰 | 0.15 |
| 雨 | 0.05 |

- **Greedy**：选“蓝”。
- **Temperature**：作用在 softmax 前的 logits 上；较低通常让分布更集中，较高通常让分布更平。下表展示的是已经归一化后的示意概率，不能直接把概率乘或除 temperature。
- **Top-k=2**：只保留“蓝、晴”，随后重新归一化。
- **Top-p=0.8**：按概率从高到低累计，保留达到 0.8 所需的最小候选集合（这里是“蓝、晴”），再对保留项重新归一化。

这些策略改变输出分布，不负责核验“蓝”是否符合事实。相同模型、相同上下文和相同解码参数在严格确定性实现中通常可以复现；使用随机采样，或实现存在数值非确定性（例如某些并行归约、精度和调度差异）时，结果可能变化。并发调度不是必然改变答案的原因，必须结合具体实现和日志核对。

## KV Cache 与固定状态不是一回事

标准注意力保存随序列增长的 Key/Value；线性注意力或状态空间模块可把历史压入固定形状的状态，避免单步状态内存线性增长。压缩可能丢失细节，因此固定状态不等于无损记住无限历史。混合架构常让多数层低成本更新，少数标准注意力层补充精确检索。

要比较推理内存，应同时写清层数、状态或缓存形状、数据类型、batch 和上下文长度，不能只比较架构名称。KDA 的状态读写见 [外积与状态矩阵](../03-数学急救包/06-外积与状态矩阵.md)。

## 幻觉放在运行链的哪里看

训练目标与数据塑造参数；上下文提供本次信息；前向计算产生 logits；解码选择 token；应用层负责检索、核验、拒答或工具调用。知识缺口、上下文冲突、推理错误、解码、检索和验证都可能造成幻觉，不能只怪“随机采样”。
