# GLM-5：长任务与稀疏注意力

> 学习导航：本页把 GLM-5 的长任务报告读成“访问路径优化”的案例，重点理解稀疏注意力解决的是计算路线，不是事实性本身。

## 论文回答什么

当上下文从几千 token 变成几十万甚至更长，完整注意力需要反复读取大量历史，成本随序列长度快速上升。GLM-5 报告把稀疏注意力、异步 Agent RL 和长软件任务放在一起，研究“模型怎样在长轨迹中找到需要的历史并继续行动”。

```mermaid
flowchart LR
  A[长文档/长轨迹] --> B[索引或路由候选历史]
  B --> C[稀疏注意力读取]
  C --> D[模型规划与工具调用]
  D --> E[环境反馈]
  E --> A
```

## 核心机制：四层别混

- **访问层**：DSA 等机制减少每个 query 要看的 key/value 数量。
- **表示层**：缓存、压缩或索引决定历史以什么形式保存。
- **训练层**：长上下文数据和 RL 使训练后的参数更倾向于在这种访问规则下工作。
- **任务层**：Agent 需要工具、权限和失败恢复，不能靠注意力机制独立完成。

如果只改变访问层，模型可能更快却漏掉关键证据；如果只增加上下文，事实也不会自动变正确。长上下文首先是“能否找到证据”的问题，其次才是“能否正确使用证据”。

## 训练与推理分开

训练时要让稀疏模式看到足够多的长距离依赖，并验证梯度和路由稳定。推理时收益取决于序列长度、稀疏比例、索引开销、内核实现和 batch；短请求或没有专用内核时，稀疏方案可能反而变慢。

## 数字证据账本

| 要对账的数字 | 需要同时记录 |
|---|---|
| 上下文长度 | token 定义、位置编码、是否训练过该长度 |
| 稀疏访问比例 | 全注意力基线、索引时间、命中率 |
| Agent 任务完成率 | 工具、重试、环境、思考预算 |
| 端到端吞吐/延迟 | 硬件、batch、并发、网络和缓存 |

教学例子：全注意力每步读取 100 个历史块，稀疏策略读取 20 个，读取量下降 $80\%$；但若索引本身增加 15 个块的开销，净读取并不是简单的 20 个。先画清“候选、索引、实际读取”三步再算速度。

## 代价与边界

- 稀疏访问可能漏掉低频但关键的证据，需用长文档检索和“证据在非热点位置”的反例验收。
- 异步 RL 改善的是采样与训练的等待关系，不自动保证奖励正确或事实可靠。
- 报告中的组合结果不能拆成“DSA 单独带来多少”“RL 单独带来多少”，除非有相应消融。

## 本课验收

**L1 · 直接应用**：稀疏注意力首先优化了什么？

<details><summary>参考答案</summary>

它优化每个位置访问历史 key/value 的计算路径与缓存成本；不是直接增加知识或验证事实。

</details>

**L2 · 变形迁移**：为什么短上下文下稀疏方案可能没有收益？

<details><summary>参考答案</summary>

固定索引、路由和内核调度开销可能超过少读几项历史的收益；收益要绑定长度、batch 和实现。

</details>

**L3 · 构造反例**：设计一个测试，专门检验稀疏访问漏证据。

<details><summary>参考答案</summary>

把唯一关键事实放在长文档中不显眼的位置，要求模型引用它并回答组合问题，同时记录检索命中、回答正确率和延迟。

</details>

**L4 · 多概念综合**：长 Agent 任务失败时，按什么顺序定位？

<details><summary>参考答案</summary>

先查关键证据是否进入候选和实际读取，再查模型是否正确规划，然后查工具/环境返回，最后查服务调度和权限；不要先把所有失败归因给模型参数。

</details>
