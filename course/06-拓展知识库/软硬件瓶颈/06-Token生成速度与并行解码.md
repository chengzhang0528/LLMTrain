# Token 生成速度：为什么通常一次接受一个

> **学习导航**：这是一篇把 D07 的运行链、推理引擎和推测解码接成一条性能主线的专题。学完后，你应能回答：一个输出 token 的时间花在哪里，哪些计算能并行，为什么普通路径仍然逐 token 推进，以及模型、算法、引擎和硬件分别能做什么。

## 本课目标

完成本课后，能够：

- 用因果概率解释普通解码为什么通常一次接受一个 token；
- 在一次基础 decode 循环的时间线上标出调度、Transformer Block、LM Head、token 选择和交付；
- 区分层内并行、请求间并行、候选验证并行与 token 接受顺序；
- 根据 TTFT、TPOT、吞吐和尾延迟，把提速问题定位到模型、算法、引擎或硬件层。

## 为什么要学这一课

“模型一次只能生成一个 token”“GPU 这么强为什么还慢”“是不是 vLLM 的采样算法决定了质量”都是实际使用中反复出现的问题。只背 `TPOT`、连续批处理或推测解码的定义，仍然无法判断某次优化究竟减少了哪段等待。本课把这些现象放回同一条执行时间线，帮助你从用户体验倒推系统瓶颈，也能看懂各模型厂和推理平台为什么同时研究架构、算法、内存、kernel、调度与硬件。

## 先回答用户真正的问题

你看到回答一个字一个字流出，很容易得出两个猜想：

- 模型是不是只能一次算一个 token？
- 如果 GPU 可以并行，为什么不一次算出后面的一整句？

关键区别是：**计算可以大量并行，接受的结果却通常要按因果顺序推进。**“一次输出一个 token”描述的是基础自回归解码的接口，不是说硬件每次只做一个乘法。

## 为什么后一个 token 不能随便提前算

因果语言模型把一段续写的概率拆成：

$$
P(x_{t+1},x_{t+2}\mid x_{\le t})
=P(x_{t+1}\mid x_{\le t})
\times P(x_{t+2}\mid x_{\le t},x_{t+1})
$$

第二项的条件里已经包含**最终接受的** `xₜ₊₁`。在它还没有确定前，模型无法知道第二步应当以哪个 token 为条件。即使最高分候选看起来很确定，也不能把“猜测”当成“已经接受”。

因此普通路径是：

```text
已确认前缀 → 计算下一个位置的 logits → 解码接受一个 token
       ↑                                  ↓
       └──────── 把新 token 纳入下一轮条件 ────────┘
```

这不是 GPU 不够快，而是模型的概率分解有依赖。它也不是绝对规律：只要先用某种方法提出后续候选，再让目标模型在候选已知时验证，就可能一次接受一段前缀。

## 哪些能并行，哪些仍有顺序

| 位置 | 可以并行的工作 | 不能直接并行的原因 |
|---|---|---|
| 一个 Transformer Block 内 | 矩阵乘法的许多乘加、向量元素运算、词表分数的批量计算 | 归一化、Attention、MLP、残差之间仍有局部依赖 |
| 同一轮的候选评分 | 候选 token 已知后，目标模型可用一次带因果遮罩的批量前向同时评分多个位置 | 候选本身必须先由草稿或其他机制提出 |
| 多个请求 | 连续批处理把不同请求的 token 合并给设备执行 | 每个请求的输出仍受自己的已接受前缀约束 |
| 多个回答 | 同时采样多条完整候选 | 这是增加探索，不会让单条回答更快完成 |
| 普通自回归的后继 token | 不能在不知道 `xₜ₊₁` 时独立确定 `xₜ₊₂` | `xₜ₊₂` 的条件包含 `xₜ₊₁` |

## 一个 token 的时间线：慢在哪里

下面从“上一 token 已经显示”到“下一 token 显示”观察一次稳态 decode。这里描述的是**客户端可见的相邻 token 间隔**教学拆分，可能包含服务端同步、网络和前端交付；引擎 profiler 的 TPOT 通常从引擎内部阶段计时，不能把两者混为一谈。数字是**教学用的 30 ms 示例**，不是任何具体模型或 GPU 的 Benchmark；真实服务要用 profiler 按 kernel、批次和硬件重新测量。

| 阶段 | 示例耗时 | 这一段实际做什么 | 常见主导因素 |
|---|---:|---|---|
| 调度与 batch 组装 | 1.5 ms | 选择本轮运行的请求、分配 token 预算和 KV 块 | 队列、连续批处理、请求长短差异 |
| Embedding 与全部 Transformer Block | 24 ms | 读权重；逐层做归一化、Attention、MLP、残差，并读写当前位置与历史 KV | 活跃参数、HBM 带宽、KV 长度、kernel 与跨卡通信 |
| LM Head 与 logits | 2.5 ms | 把最后位置隐藏向量映射到词表的全部候选分数 | 词表大小、矩阵布局、量化格式 |
| 解码选择 | 0.5 ms | 应用 temperature、top-k/top-p 或 greedy，接受一个 ID | 采样实现、排序/筛选和随机数 |
| 同步与流式交付 | 1.5 ms | 等待结果、追加状态并把 token 交给服务和客户端 | 同步点、网络、序列化与前端刷新 |
| **合计** | **30 ms** | 从一个已显示 token 到下一个已显示 token 的教学拆分 | 分类会随实现变化，不能直接横向套用 |

`0.5 ms` 的采样只是示例中的一小段。即使它完全优化掉，24 ms 的模型前向仍在；所以“模型输出随机，是不是采样算法拖慢了”通常不是首要诊断方向。采样会影响结果分布，确实可能有排序、筛选和同步成本，但它通常不承担主要的 TPOT。

### 首 token 与后续 token 要分开看

- **TTFT（首 token 延迟）**：应用端通常包含排队、模板和 tokenizer、检索或工具等待、完整提示的 prefill、首个 logits 与交付；引擎端通常从请求到达引擎后开始。
- **TPOT（每 token 延迟）**：同一测量边界下，首 token 之后的平均间隔，常用来观察 decode；应用端间隔还会受网络和网关缓冲影响，引擎端则主要反映前向、缓存和调度。
- 输入变长优先怀疑 TTFT；生成中每 token 变慢优先查看 TPOT、KV Cache、显存带宽和调度；并发一上去尾延迟暴涨，则先看队列与 P95/P99。

不要用单一 `tokens/s` 把三种体验混在一起。单请求稳态下可以粗略用 `1000 ÷ TPOT(ms)` 估算输出速度，例如 `TPOT = 25 ms/token` 约等于 `40 token/s`；有 batch 时还要另报系统总 token 吞吐和每用户延迟。

## 从不同责任层提速

| 责任层 | 主要办法 | 它改变的对象 | 不能直接承诺 |
|---|---|---|---|
| 模型架构 | 缩小活跃参数、稀疏 MoE、GQA/MQA/MLA、训练支持的 MTP | 每轮要算的矩阵量、KV 体积或可提议的候选数 | 参数少就一定质量不变；MTP 训练监督就等于一次接受多个 token |
| 模型资产与数值表示 | 权重、激活或 KV Cache 的量化与混合精度 | 搬运字节数、显存容量、量化误差与格式适配 | 位宽降低就必然同比加速，或量化只由硬件决定 |
| 解码算法 | 推测解码、候选树、自推测、块式或非自回归路线 | 目标模型串行前向次数或接受方式 | 候选数就是接受数；任何实现都无损或都加速 |
| 引擎与 kernel | 连续批处理、分页 KV、前缀缓存、分块 prefill、算子融合、图执行 | 调度、内存碎片、重复启动和请求间空转 | 所有优化同时降低 TTFT、TPOT 和尾延迟 |
| 运行硬件与分布式 | HBM 带宽、张量/专家并行、互联与拓扑优化 | 权重搬运、单卡容量和多卡协作成本 | 标称 FLOPS 高就一定适合 decode；多卡一定比单卡快 |

### 为什么各模型厂都在研究这件事

速度瓶颈不是一个“神奇采样器”能解决的单点问题，而是全生命周期的账：更大的模型通常带来更强能力，也带来更多权重读取、更大的 KV 和更高通信成本；更激进的量化或稀疏化可能省内存，却需要匹配 kernel 并验证质量；推测路径能减少目标模型的串行前向次数，却要支付草稿和验证的额外成本。模型厂、推理框架和硬件厂商因此分别优化结构、训练目标、解码算法、内存布局、kernel、调度和互联，并用同一质量与 SLO 合同验收。

## 看到症状，先定位哪一层

| 现象 | 先看什么 | 可能的下一步 |
|---|---|---|
| 首 token 明显慢，后续正常 | TTFT、输入长度、队列与检索时间 | 分块 prefill、前缀缓存、减少无效上下文或改善排队 |
| 首 token 正常，但回答一字一字很慢 | TPOT、KV 读取、HBM 带宽、活跃参数 | KV 形状/精度、kernel、量化、架构或推测解码 |
| 单请求很快，并发后变慢 | P50/P95/P99、batch 组成、显存水位 | 连续批处理、分页 KV、限流与 SLO 分层 |
| tokens/s 很高，用户仍觉得卡 | TTFT、首包与端到端延迟 | 重新区分总吞吐与单用户体验，检查队列和流式交付 |
| 加了推测解码却没有收益 | 接受长度、草稿耗时、验证耗时、batch | 只在目标模型串行 decode 是主瓶颈且接受率足够时保留，否则回退 |

## 方法边界

1. **并行采样多条回答**是多开请求，不是让一条回答的后继 token 摆脱因果依赖。
2. **MTP**可以提供多 token 预测监督或候选，但是否能在推理时一次接受多个 token，要看模型结构、训练方式和引擎支持。
3. **推测解码**减少的是目标模型的昂贵串行前向次数；满足相应接受/校正规则时，才可以声称保持目标分布，近似实现要单独评估。
4. **非自回归或扩散式文本模型**可以把多个位置作为一个整体反复修订，但它们改变了建模目标和生成接口，不能当作现有因果模型的通用开关。
5. **速度提升不等于能力提升**。任何对照都要同时报告质量、TTFT、TPOT、吞吐、显存、P95/P99、错误率和回退条件。

## 本课验收

- 为什么 `xₜ₊₂` 不能在 `xₜ₊₁` 尚未接受时直接确定？
- 普通 decode 一轮里，哪些矩阵工作并行，哪些 Block 依赖仍然顺序？
- 30 ms 教学拆分里，为什么采样只占 0.5 ms 不能代表“模型很快”？
- 推测解码何时可能加速，何时草稿成本会抵消收益？
- 看到 TTFT、TPOT、吞吐或尾延迟异常时，你会先查哪一层？
