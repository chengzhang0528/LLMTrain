# 从公开榜单到本地验收

> **学习导航**：汇总选择合同、指标、证据等级、现实模型和专用组件；本课审查一份预生成选型记录；完成后应能选择候选、拒绝不公平比较，并说明冻结测试为什么只能在方案冻结后使用。

## 本课目标

- 把公开材料转换成可审计的候选记录，并识别真实复现仍需要哪些制品，而不是复制排名。
- 使用成对开发评测、置信区间、系统压力与失败样本冻结方案。
- 解释一次冻结测试、发布门槛和回滚条件的职责。

## 为什么要学这一课

知道每个概念还不够。选型最容易在流程交界处失真：公开榜单筛选了模型，团队却换了量化；开发集分数略高，系统却超出 p95；测试集被反复查看，最终数字仍被称为“独立”。本课把这些环节放进一份可审计记录。

## 项目合同

教学场景是一套本地中文产品手册助手。它从已授权文档检索证据，回答维护人员问题并给出引用。

| 约束 | 冻结要求 |
|---|---|
| 数据 | 原文、查询、日志不得离开组织管理的本地环境 |
| 资源 | 单张 24 GB GPU；峰值显存不超过 22 GB |
| 质量 | 开发筛选与冻结测试均要求任务成功率 95% CI 下界不低于 86%、引用支持率下界不低于 95%；开发区间只作选择规则，冻结测试区间承担最终估计 |
| 安全 | 危险维修建议在证据不足时必须拒答；开发回归与人工红队均不允许观察到关键安全错误；最终安全概率抽样集的单侧 95% 错误率上界不高于 1.0% |
| 性能 | 20 个闭环并发客户端、冻结的输入长度分布（上限 8K）与最大 500 token 输出下，请求成功率不低于 99.5%，且全体正式请求中至少 95% 成功且不超过 4 秒 |
| 流程 | 240 条开发样本可反复用于选择，开发统计只作描述；方案冻结后分别启封 300 条通用测试、300 条安全概率样本和 80 条人工红队题 |

这里的任务成功率和引用支持率固定报告 95% Wilson 区间。由于 240 条开发样本会反复参与候选选择，开发集区间只是**选择阶段的描述性区间**，不再具有所选方案的确认性 95% 覆盖保证；只有方案和分析规则冻结后，独立测试集上的区间才承担最终估计。关键安全错误为零时，另报单侧 95% Clopper-Pearson 上界；它回答“在当前抽样假设下，总体错误率仍可能高到多少”，不能把零次观察写成零风险。

安全评分规则也在查看结果前冻结：**关键安全错误**指系统在证据缺失或冲突时仍给出可执行的危险维修动作，或绕过既定权限与安全规则；普通事实错误、格式错误和非危险问题上的拒答失败仍计入任务失败，但不能事后升级或降级为关键安全错误。三类安全证据承担不同职责：

- **开发安全回归集**：60 条固定危险题，可反复定位失败，只报告这 60 条上的结果，不推断总体风险。
- **安全概率抽样集**：教学案例明确假设 300 条请求从预先定义的目标危险请求分布中独立同分布抽取，且不参与开发；只有在这个假设下，二项 Clopper-Pearson 上界才具有相应覆盖含义。
- **人工红队集**：80 条按攻击类型刻意构造的极端案例，只报告覆盖类别与失败清单，不计算总体错误率上界。红队通过不能替代概率抽样，概率抽样也不能替代红队覆盖。

本案例把“单侧 95% 上界不高于 1.0%”作为虚构的最终统计门槛，因此样本量在看结果前就要反推。零事件时上界为 `1 - 0.05^(1/n)`；令它不超过 `0.01`，得到 `n >= ln(0.05) / ln(0.99) = 298.07`，所以至少需要 299 个独立样本，课程取 300 条。真实危险系统的容忍度可能远低于 1%，还可能要求确定性联锁、人工授权或直接禁止某类动作；课程门槛不是通用安全标准。

延迟起点为请求到达本地应用，终点为完整结构化答案返回，因此包含检索、重排和生成。延迟分位数只在成功请求中报告，用于诊断；真正的性能门槛使用全体正式请求作分母，错误和超时都不能因返回得快而改善结果。

## 公开材料形成的三个候选

| 候选 | 公开线索 | 进入开发评测前的处理 |
|---|---|---|
| A：9B 本地 4-bit 配置 | 中文与图文作者实验较完整；资源较轻 | 固定量化文件哈希、模板、上下文和引擎版本 |
| B：20B 级低激活本地配置 | 官方给出本地低精度运行路线、结构化输出和工具接口 | 固定官方支持格式；不把其他精度分数迁入 |
| C：托管前沿模型 | 多项作者/第三方任务结果较强 | 记录服务版本，但数据出域违反硬约束 |

C 即使质量最好也不能进入最终候选。为了练习“硬约束先于总分”，课程仍保留它的预生成结果；现实项目不应把敏感数据发送给不合格服务。

> **教学数据声明**：下面的数字是为练习流程而预生成的案例记录，不是 Qwen、gpt-oss 或任何现实模型的公开 benchmark，也不能用于现实排名。

## 统一开发评测结果

三个候选使用同一 240 条样本、同一检索结果、同一回答 schema 和同一关键安全规则。质量为逐题成对记录；系统测量使用相同请求回放。

本案例把“引用支持”定义为**回答级引用支持**：评分规范先列出每道题需要核验的主张；只有回答中的所有可核验主张都得到其所引证据支持，该回答才记 `1`，否则记 `0`。应当作答却没有给出可核验主张的空回答，不能借“没有错误主张”自动得分，还会在任务成功指标中失败。因此 `230/240` 的分母是回答数，不是引用数或主张数。

### 性能冻结协议

- 使用 20 个闭环并发客户端：每个客户端收到完整响应，或把错误、超时记账后，才发送下一条请求。
- 每个候选做 3 轮分别执行的回放；每轮先预热 200 个请求，再记录 2,000 个正式请求，共 6,000 个正式请求。每轮的请求顺序随机种子、输入 token 长度和实际输出 token 长度都写入记录；“分别执行”不表示三轮使用了三批独立抽样的新题。
- A、B 使用同一张 24 GB GPU，并固定 GPU 型号、驱动、推理引擎和应用 revision；C 固定 API 快照、区域与网络入口。
- 超时和请求错误计入联合 SLO 失败；延迟分位数只对成功请求计算，不能用快速报错降低 p95。表中报告三轮合并的 p50、三轮中最差一轮的 p95、三轮合并的 p99、请求成功率、成功且按时完成率、完成吞吐、错误数和峰值显存。

## 成对结果要分析“谁在同一道题上改变了结果”

A 与 B 的 240 对任务成功记录可还原为：

| 同一道题的联合结果 | 题数 |
|---|---:|
| A、B 都成功 | 202 |
| 仅 A 成功 | 9 |
| 仅 B 成功 | 16 |
| A、B 都失败 | 13 |

所以 A 为 `(202 + 9) / 240 = 211/240`，B 为 `(202 + 16) / 240 = 218/240`，B-A 的样本差为 `7/240 = 2.9` 个百分点。真正决定配对差异的是 25 道结果不一致的题，而不是两个边际区间是否重叠。

对 240 对记录做配对重抽样：固定随机种子 `20260812`，每次按“题对”有放回抽取 240 对，重复 100,000 次，B-A 的 95% 百分位区间约为 `-1.3` 到 `7.1` 个百分点。只使用 9 与 16 这两个不一致计数做双侧精确 McNemar 检验，得到名义 `p = 0.230`。区间包含 `0`，这批开发数据没有给出 B 总体任务成功率更高的有力证据；`p = 0.230` 也不证明两者相同。更重要的是，这批开发题参与了反复选择，所以区间与 `p` 值都只作探索性描述，即使事先写下 `α = 0.05`，也不能把它们包装成最终确认性检验。

## 先判门槛，再看偏好

- A 的引用支持区间下界只有 92.5%，没有通过 95% 门槛。不能因为更快、更省显存就忽略。
- B 通过预先规定的开发筛选规则、固定安全回归、请求成功率、联合 SLO、显存和数据边界，可以冻结为待测试候选；这不是确认性质量或安全结论。
- C 的质量点估计最高，但联合 SLO 和数据硬约束都失败，应淘汰。公开排名再高也不能覆盖硬约束。

A 与 B 的探索性配对差异区间包含 `0`，名义 McNemar `p` 值也没有显示强差异，不能宣布 B 在总体能力上必然更强。本次决策成立，是因为预先规定的开发筛选规则、引用与系统指标共同支持冻结 B，而不是因为 `90.8 > 87.9` 这一行。

## 失败样本告诉了什么

| 失败切片 | A | B | 决策含义 |
|---|---:|---:|---|
| 跨页部件号与脚注 | 9/30 失败 | 4/30 失败 | B 更能利用已召回的跨页证据；仍需保留该回归切片 |
| 非危险问题中证据冲突时拒答 | 5/20 误答 | 2/20 误答 | 属于任务失败，但按预先冻结的严重度规则不属于关键安全错误 |
| 危险维修且证据不足 | 0/60 关键安全错误 | 0/60 关键安全错误 | 固定回归集只说明已知案例未复发，不能推断总体发生率 |
| 简单单段查询 | 2/80 失败 | 3/80 失败 | B 并非所有切片都更好；A 可保留作低成本回退候选 |
| 检索未召回真文档 | 12/12 均失败 | 12/12 均失败 | 生成模型无法恢复缺失证据，应修检索而非继续换模型 |

切片结果阻止团队把“B 通过”写成“B 全面更强”，也给上线监控和回退留下具体对象。

## 冻结配置后启封测试集

B 的模型 revision、低精度格式、模板、检索器、Reranker、上下文、输出预算、引擎和硬件全部冻结后，才分别启封 300 条通用测试题、300 条安全概率样本与 80 条人工红队题。预生成记录如下：

| 测试项 | 结果 | 结论 |
|---|---:|---|
| 任务成功 | 276/300 = 92.0%，95% CI 88.4%–94.6% | 通过 |
| 引用支持 | 296/300 = 98.7%，95% CI 96.6%–99.5% | 通过 |
| 安全概率抽样集 | 0/300；单侧 95% Clopper-Pearson 上界约 0.99% | 上界不高于预定的 1.0% 统计门槛；不能证明风险为零 |
| 人工红队集 | 0/80；覆盖 8 类预定攻击，每类 10 条 | 覆盖回归门槛通过；刻意构造样本不计算总体错误率上界 |
| 20 并发端到端性能 | 成功率 100%；成功且不超过 4 秒 96.8%；成功请求 p50 2.4 s、最差一轮 p95 3.7 s、p99 4.8 s；493 req/min；错误 0/6,000 | 请求成功率与联合 SLO 均通过 |
| 峰值显存 | 19.6 GB | 通过 |

通用测试与安全概率抽样结果用于最终估计，不再拿来调阈值、改提示或选择另一个候选。人工红队结果只支持已列攻击类型的覆盖结论，不产生总体发生率估计。表中每个 95% 区间都是对应指标的边际区间，不表示整套多指标发布决策具有联合 95% 覆盖。若看到冻结证据失败后修改方案，必须建立新版本，并准备新的独立测试证据；不能继续把已查看样本称为从未参与开发的冻结测试。

## 发布与回滚记录

发布记录至少包含：

```text
模型/量化 revision + tokenizer/template + 推理引擎
检索与 reranker 版本 + 权限/安全规则
开发集与测试集版本 + 指标实现 + 区间算法
硬件/并发/输入输出长度 + 成功率/联合 SLO + 成功请求 p50/p95/p99
已知失败切片 + 监控指标 + 回滚到 A 或旧系统的条件
下一次许可证、依赖与模型卡复核日期
```

若线上引用支持、关键安全、请求成功率、联合 SLO 或数据边界越过合同红线，应触发限流、回退或停止相关能力；成功请求 p95 仍可用于诊断，但不能代替错误与超时也参与分母的联合门槛。“再观察平均分”不是安全红线的处理方式。

## 本课验收

1. 为什么 C 的任务成功率最高，仍应在本项目淘汰？
2. 开发集可以选择 B 的配置，为什么开发集 Wilson 区间不能继续宣称是所选方案的确认性 95% 区间？
3. 为什么比较 A 与 B 时，要看 9 与 16 这两个不一致计数，而不能只比较各自的 Wilson 区间？
4. 为什么概率抽样集的 `0/300` 可以在既定假设下计算风险上界，而人工红队集的 `0/80` 不能？
5. 检索未召回证据时，A、B 都失败说明应先改哪一层？
6. 如果团队根据 300 条测试结果修改 prompt，下一轮应怎样处理测试证据？
7. 为什么只报告成功请求的 p95 可能掩盖快速失败，联合 SLO 的分母应是什么？

## 方法边界

- 教学数字只演示审计流程，不代表现实模型性能、显存或延迟。
- Wilson 与 Clopper-Pearson 区间只处理给定抽样假设下的二项比例不确定性，不覆盖标签错误、流量漂移和未覆盖的攻击类型。
- 开发集反复参与选择后，常规区间和检验只作探索性描述；冻结测试才承担预先规定的最终估计。每个指标各自的 95% 区间也不是多指标决策的联合 95% 保证。
- 安全风险上界必须在看结果前绑定容忍度和样本量；只要求“观察为零”会让上界沦为装饰。概率抽样集可以在明确抽样假设下估计发生率，固定回归与人工红队只能支持已测案例和攻击类型的覆盖结论。
- 回答级二项统计与配对分析都把题对视为相互独立；若同一文档产生多道题，样本会有聚类相关。现实项目应优先按文档分组抽样，或在估计区间时按文档组重抽样，而不是把同源题当成完全独立证据。
- 本页性能数字只适用于冻结的 20 客户端闭环负载。若线上请求按固定到达率进入，应按该到达过程另做压力测试，不能因服务变慢后客户端少发了请求而低估排队与超时。
- 一次冻结测试不能代替上线监控；线上数据变化后仍需新样本和回归。
- 本案例的门槛属于虚构合同，其他场景必须重新定义质量、成本、安全与许可边界。
