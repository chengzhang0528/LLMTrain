# 数据、模型与系统联合设计

> **学习导航**：承接方法选择；本课把数据、模型和应用系统放在同一张接口图上；完成后应能为最终错误指出可检查的责任层。

## 本课目标

画出从原始输入到最终输出的数据流，标明每层输入、动作、输出、版本和失败日志。

## 为什么要学这一课

上线质量不等于模型分数。解析器会丢字段，检索器会漏文档，工具会超时，模型会误读证据，服务层也可能截断上下文。联合设计能把失败定位到真实环节，而非统称“模型不够强”。

## 四层接口

| 层 | 输入 | 输出 | 必留日志 |
|---|---|---|---|
| 数据层 | 原始文本、图像、表格、事件 | 清洗样本、索引、特征 | 来源、版本、许可、切分 |
| 模型层 | token 或模态表示 | logits、类别、结构化字段 | 模型、模板、精度、解码 |
| 工作流层 | 模型输出、检索、工具状态 | 候选答案或动作 | 中间状态、错误、重试 |
| 服务层 | 用户请求、权限、负载 | 最终响应 | 延迟、队列、权限、版本 |

## 案例 B：带引用问答的系统接口

前两课用工单路由说明任务合同和基线阶梯。本课暂时切换到带引用问答，因为它更容易展示解析、检索、模型、核验与服务之间的接口；下一课的验收矩阵会回到工单路由。两个案例承担不同教学任务，不代表同一个项目中途更换目标。

`文档 -> 解析 -> 切分 -> 建索引 -> 检索 -> 重排 -> 组装上下文 -> 模型生成 -> 主张与引用核验 -> 权限过滤 -> 输出`

每个箭头都要定义数据格式。例如检索结果至少包含文档 ID、片段位置和分数；最终引用必须能回到相同 ID，不能只显示一个看似可信的链接标题。

## 训练与系统改动分开

模型微调时固定检索版本；优化检索时固定模型与提示。否则最终提高无法归因。确需联合优化时，也要先完成各层独立基线，再进入联合实验。

## 预设案例观察

五份冻结故障日志如下；定位依据必须来自中间状态，而不是最终回答的语气：

| 日志 | 关键记录 | 优先定位 |
|---|---|---|
| L-01 空文档 | 解析后字符数为 0，原文件大小 2.1 MB | 数据层：解析失败 |
| L-02 错误检索 | top-5 文档 ID 均不属于退款政策库 | 数据层：索引或检索失败 |
| L-03 工具超时 | 工具返回 `timeout`，模型前向尚未开始 | 工作流层：工具调用失败 |
| L-04 格式错误 | 模型原始输出缺少 `source_id`，服务未拦截该输出 | 模型层：结构化输出失败 |
| L-05 上下文截断 | 组装后 11,200 token，服务只传入最后 8,192 token | 服务层：输入截断 |

L-05 最终可能表现为“模型不知道政策”，但日志证明政策片段在进入模型前已被截掉；继续微调模型并不能直接修复这条数据流错误。

## 本课验收

1. 检索结果没有文档 ID 会妨碍什么核验？
2. 为什么模型微调与索引更新应先分开实验？
3. 服务层截断上下文可能伪装成哪类模型失败？
4. 哪些中间状态不应因“节省日志”而完全丢失？

## 方法边界

日志需要遵守隐私、权限和保留期限，不能为了可观测性保存全部敏感输入。可追溯与数据最小化必须共同设计。
